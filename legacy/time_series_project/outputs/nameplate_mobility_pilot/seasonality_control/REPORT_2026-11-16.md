# Controlled seasonal-period check

## Question

Does the apparent gain from Naver search survive when the seasonal reference changes from 13 weeks to 52 weeks?

This is a **new controlled sensitivity check**, not a rerun of the original statsmodels SARIMA. The local Python environment lacked statsmodels, so `run_seasonality_control.py` fits a conditional AR(1) regression to seasonally differenced `log1p` weekly mobility. The same model equation is fitted with seasonal period 13 and 52. Comparisons **within this check** hold the dong cohort, target, origin, forecast weeks, search series, and feature construction fixed. The original SARIMA and this check have different equations and must not be compared as if only one parameter changed.

## Setup

- Target: weekly mean of daily destination mobility for ages 20–39, purposes 4+5+7.
- Cohort: the same 419 administrative dongs with complete weekly mobility and mapped Naver search.
- Origin: information through 2025-04-27; one fixed forecast for 2025-04-28 to 2025-07-27 (13 complete weeks).
- Search: the same lagged monthly Naver `index` used in the original experiment; future forecast inputs come from completed months no later than 2025-03.
- Mobility input: the same target 13 weeks earlier, known at the origin.
- Score: pooled WAPE over 419 × 13 = 5,447 dong-weeks. Smaller is better.
- Seasonal-difference regression: `z[t] = log1p(y[t]) - log1p(y[t-s])`; fit `z[t]` on `z[t-1]` and optional seasonally differenced inputs. All models for a given `s` use the same training rows. Forecast 13 `z` values recursively and add the observed `log1p(y[t-s])`. Both `s=13` and `s=52` use only values known at the cutoff.
- The raw training calendar is the same, but seasonal differencing leaves 94 fitted weekly rows for `s=13` and 55 for `s=52`. This unavoidable sample-length difference is a limitation of the seasonal-period comparison.

## Pooled WAPE (%)

| Seasonal period | No extra input | + 13-week-lagged mobility | + lagged mobility and Naver search |
|---|---:|---:|---:|
| 13 weeks | 19.45 | 11.11 | 13.10 |
| 52 weeks | **8.59** | 8.83 | 14.43 |

The prior-year same-week baseline from the original experiment scored **8.52%** on the same 419 dongs and 13 weeks. The old fixed-order SARIMAX scored **18.93%** with lagged mobility and **16.28%** after adding search. Those old model numbers are context, not direct counterparts of the new seasonal-difference regression. The actual target values in all 5,447 test rows were checked against the original backtest and matched exactly.

Search worsened pooled WAPE by **1.99 percentage points** with `s=13` and **5.60 points** with `s=52`, relative to the same regression with lagged mobility and no search. It improved only **163/419** dongs with `s=13` and **127/419** dongs with `s=52`. This supports the concern that the old search gain is model-specification-dependent; it does **not** show that search can never help a particular dong or forecast origin.

An intercept in the seasonal-difference equation was also tested, holding all else fixed. It worsened the no-input WAPE from 19.45% to 20.88% for `s=13`, and from 8.59% to 15.41% for `s=52`. Thus simply adding this form of drift did not solve the forecast bias. These are sensitivity results, not a comprehensive test of trend models.

## Interpretation for the presentation

The original search improvement is a valid result **conditional on its original 13-week seasonal specification**. It is not evidence that search is a stable predictor across seasonal assumptions. A defensible statement is: *“Search improved our initial specification, but the gain did not persist in a controlled annual-seasonality check; its value remains inconclusive.”*

This check does not validate or invalidate the 4+5+7 target as a hot-place proxy; target validity must be assessed separately. It also does not identify the external cause of any particular dong's decline.

Outputs: `predictions.csv` (all 65,364 forecasts), `pooled_wape.csv`, and `per_dong_wape.csv`. The five-dong `predictions_smoke.csv` records the pre-run smoke check and is not used for conclusions.
